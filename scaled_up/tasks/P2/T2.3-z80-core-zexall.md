## Context
We do NOT hand-write or hand-translate a Z80 core — a de-novo translation is
writing a core (see cdoc/decisions.md). The core must pass the standard
exercisers before any trace from it is trusted. Per-opcode JSON tests give
pinpoint failures; zex gives only end-of-group CRCs — use both.

## Entry criteria
- [x] T2.1 done (`cd machine && npm test` passes -> 8/8).
- [x] `zexdoc.com`/`zexall.com` in `machine/fixtures/` (8704 bytes each).

## Task
1. Delete the hand-translated `machine/src/cpu/z80.js` opcode implementation.
2. Vendor a real core, preferred order:
   a. DrGoldfire/Z80.js as-is (MIT). Known deviation: undocumented X/Y flag
      behavior in BIT n,(HL) — characterize via step 4 and record in
      decisions.md (1980s arcade code cannot plausibly depend on it).
   b. If (a) proves unsuitable: superzazu/z80 C compiled to WASM via emcc,
      vendored as a binary artifact (mechanical transform, logic preserved).
3. Keep the thin swappable interface in `machine/src/cpu/` (memory/IO
   callbacks, per-instruction step, cycle counts, IRQ/NMI lines).
4. Build `machine/tools/run_sst.js`: runner for the SingleStepTests/z80 JSON
   suite (github.com/SingleStepTests/z80) — per-opcode, ~1000 cases each.
   Register-and-memory comparison mode is sufficient (cycle/bus-level
   comparison out of scope). Record pass/fail counts per opcode; documented
   known-deviation opcodes may be allowlisted ONLY with a decisions.md entry.
5. Keep `machine/tools/run_zex.js` as the integration gate.

## Out of scope
Hand-writing/translating opcode logic. Cycle/bus-level SST comparison.
Berzerk devices. Performance.
