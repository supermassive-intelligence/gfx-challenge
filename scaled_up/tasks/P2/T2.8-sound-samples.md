# T2.8 — Sound/speech via samples
Phase: 2   Depends-on: T2.4   Status: pending

## Context
Decision (see cdoc/decisions.md + plan Phase 2): do NOT emulate the S14001A
speech chip or discrete sound circuits initially. Trigger recorded samples
keyed on the CPU's writes to the sound/speech ports. CPU-visible contract:
`cdoc/hardware-berzerk.md` §7. At the project's fidelity bar (feel), samples
are indistinguishable; chip emulation is a later opt-in if that proves wrong.

## Entry criteria
- [ ] T2.4 done. Spec §7 lists the write→utterance/effect mapping.
- [ ] HUMAN-GATE: sample audio files supplied by human into
      `machine/fixtures/samples/` (user-sourced; never committed).

## Task
`machine/src/sound.js`: port-write handler decoding speech commands and sound
triggers per spec → emits named events (`speech:intruder_alert`,
`sfx:laser`, ...). Audio backend is pluggable: a silent/recording backend for
tests (logs event sequence), WebAudio backend for the browser (T2.9 wires it).
Busy/ready status reads (if spec documents them) return plausible values —
note any timing approximation in cdoc/decisions.md.

## Out of scope
S14001A internals. Audio mixing quality. Browser autoplay policy (T2.9).

## Definition of done
- [ ] Unit tests: documented port-write sequences produce the expected named
      event sequence (cases cite spec §7).
- [ ] Status-read behavior tested against whatever spec documents.
- [ ] `npm test` passes (tests run silent backend; no audio files needed in CI).

## Verification
```
cd machine && npm test
```
