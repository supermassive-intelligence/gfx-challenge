### Review fixes applied (2026-06-12)
1. setIrqEnable(false) no longer clears a pending IRQ -- MAME's HOLD_LINE
   survives irq_enable_w(0). New regression test asserts: IRQ held (iff1=0) ->
   setIrqEnable(false) -> iff1=1 -> IRQ still delivered with vector 0xFC.
2. The 0x4E-read "clears pending frame IRQ" is a schematic note MAME does NOT
   implement; §5.4 + §4.4 corrected to match the oracle. scheduler.js ackIrq()
   is now HARDWARE-NOTE-ONLY (records the note; must not be wired at T2.9).

### For the human review
- The held-IRQ model: the vendored core services a maskable IRQ only when iff1
  is set (drops it otherwise) and NMI always; the scheduler holds the IRQ
  pending until iff1 acknowledges it (which clears it), matching HOLD_LINE.
  Interrupt-acknowledge cycles are counted into the frame budget via the core's
  cycle_counter delta.
- Out of scope / deferred: wiring the enable ports (0x4C/0x4D/0x4F) and the
  0x4E read (V256 -> Video.readIntercept; NO IRQ clear) into the I/O dispatch is
  T2.7/T2.9; requestAnimationFrame pacing is T2.9 (scheduler stays wall-clock-free).
- Empirical gate downstream: at T2.9 boot, the wrong cadence would desync the
  game loop; the determinism test here is the unit-level proof of the timer chain.
