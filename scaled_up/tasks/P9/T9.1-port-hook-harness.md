## Task
Add a dispatch hook in the machine: when PC hits a registered CALL target,
run the JS implementation (reads/writes shared memory, returns as if RET),
else fall through to the Z80 core. Registry of {address → JS fn}. One trivial
leaf routine ported end-to-end as the proof.

## Implementation
- `machine/src/port-hook.js` — the adapter + dispatcher (`makePortHook`).
  Builds the EXACT `ctx.{regs,flags,mem,io}` shape the T8.1 bench builds, backed
  by the LIVE core (`getState`/`setState`) + live memory/IO callbacks, and runs
  the SAME `port(ctx)` function from `machine/ports/`. One implementation, two
  callers (bench + live machine).
- `machine/src/cpu/z80.js` — `installPortHook(hook)`; `step()` consults it before
  fetching. A registered hit returns the displaced cycle cost and skips the core;
  a miss / declined call returns null → core runs the instruction.
- `machine/src/machine.js` — `installPortHooks()` wires the dispatcher (default
  registry/meta) to the cpu, passing the scheduler. OFF by default (un-hooked
  machine stays the reference); opt-in.
- `machine/src/scheduler.js` — `eventWithin(cycles)` (port-agnostic timing query).
- `machine/ports/index.js` — `PORT_META` (cycles + entry pushes) beside `PORTS`.
- `machine/tools/replay_hash{,_visible}.js` — honor `BERZERK_PORT_HOOKS=1` so the
  same tool produces hooked and un-hooked hashes.

### Cycle accounting (the load-bearing decision)
A native JS port runs in 0 Z80 cycles. The dispatcher charges the DISPLACED
routine's own cycle cost (heavy-trace `cycle_count`, entry..ret inclusive; RANDOM
= 140, matching every RANDOM test-plan `cycles`), returned to the scheduler
exactly as `cpu.step()` would, so interrupt cadence — and thus the timing-locked
V256/entropy phase (T5.1/T5.2) — is preserved.

Two subtleties were found empirically (both caused real divergence before fix):
1. **Interrupt granularity.** Charging 140 atomically defers an interrupt that
   would otherwise be serviced MID-routine to AFTER it (~1 scanline later beam
   position), shifting the ISR's V256 read and perturbing entropy. FIX: fast-path
   only when `scheduler.eventWithin(cost)` is false; otherwise DECLINE (core runs
   the real routine, byte-identical to un-hooked). When no interrupt splits the
   window, atomic charge == the 14 sub-steps exactly.
2. **Stack overlaps VRAM.** Berzerk's stack lives inside the 0x4000-0x5FFF screen
   RAM (observed sp 0x42f2). RANDOM's `push hl` therefore writes HL onto VRAM
   (0x42f0/0x42f1, visible row 23) — transient stack noise the real machine AND
   MAME produce (the T3.4 golden matched it). A register-only port omits it, so
   the hooked machine diverged from un-hooked at exactly those bytes (attract
   frames 2090, 2149) until the next draw overwrote them. FIX: the hook replays
   each routine's entry pushes (`PORT_META.pushes`) into live memory; pop/ret only
   read, so the push bytes are the sole observable stack-frame memory effect.

## Hazard Checklist (guides T9.2 — what makes a routine unsafe to fast-path)
1. **Self-modifying code** — writes to its own opcode stream; a static JS port
   cannot reflect the mutation. Run in the core.
2. **Computed jumps / jump tables** (`jp (hl)`, `jp (ix)`) — the exit target is
   data-dependent; the hook's fixed RET semantics are wrong. Port only if every
   exit is enumerated and modeled.
3. **Shared tails / mid-body entries** — other code `jp`s INTO the body past the
   entry PC (e.g. LTABLE 0x1AED `pop hl; jp (hl)`); a single entry_pc hook misses
   those entries and the routine's stack discipline is broken.
4. **Timing-contract routines** — internal instruction timing is observed by
   hardware (S14001A speech pacing, 6840 timer) or a delicately phased interrupt.
   Atomic execution changes the contract. (Partially covered by the eventWithin
   decline, but a routine whose OWN body times a device needs the core.)
5. **Coroutine / stack-swap routines** — the job system (CREATE_JOB 0x1E22 swaps
   SP between coroutine stacks; MAN_INIT 0x1FD4 `pop iy`). SP-depth pairing breaks
   (heavy-trace.md "Known limitation"); the RET-by-SP assumption is invalid.
6. **Entropy-reading routines** — read port 0x4E bit0 (V256) or the 0x089F counter
   (T5.2). They must REPLAY captured entropy, never recompute; and they must not
   be fast-pathed across an interrupt that would change the entropy phase (handled
   by eventWithin).
7. **Stack-overlaps-VRAM (discovered here)** — because the stack is inside screen
   RAM, ANY routine that `push`es leaves observable bytes in VRAM. A register-only
   port MUST declare its entry pushes (`PORT_META.pushes`) so the hook replays
   them; otherwise it diverges by transient framebuffer noise. Routines with
   complex/conditional stack use (unbalanced push/pop, push inside loops, pushing
   values the body then mutates before pop) need per-routine modeling or the core.
